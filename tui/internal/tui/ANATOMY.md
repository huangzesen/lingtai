# tui/internal/tui — Bubble Tea screens

> **Maintenance:** see `lingtai-tui-anatomy` (at `tui/internal/preset/skills/lingtai-tui-anatomy/SKILL.md`).

This is the ~20k LOC Bubble Tea v2 package that renders every screen of `lingtai-tui`. Each screen is a struct implementing `Init()`, `Update(msg)`, `View()`, living in its own `.go` file. The package is intentionally flat — breaking it into sub-packages would fight Bubble Tea's convention (every model must be the same `tea.Model` type for the dispatcher), and Go's single-type-per-package constraint makes this the grain that matches the framework.

Screen routing is centralized in the `App` struct (`app.go`), which holds every screen as a field, dispatches commands via `switchToView`, and maps the slash-command palette (`/mail`, `/setup`, `/doctor`, `/daemons`, `/notification`, `/goal`, etc.) to view transitions or narrow file-protocol actions.

## Components

### Root model and dispatcher

- **`tui/internal/tui/app.go:24-44`** — `appView` enum: 19 view constants (`appViewFirstRun` through `appViewHelp`), including `appViewNotification` for `/notification`.
- **`tui/internal/tui/app.go:51-113`** — `App` struct: holds every root-routed screen model plus routing state (`currentView`, `orchDir`, `orchName`, `recoveryMode`), the active mail generation token, and the root-owned `/projects` visit state (first/original context, preserved origin view/model, current target, and double-Esc return timing).
- **`tui/internal/tui/app.go:154-249`** — `NewApp`: constructor deciding initial view — mail view (returning user), first-run wizard (new user or rehydration), or recovery mode (global config lost, agents intact).
- **`tui/internal/tui/app.go:251-275`** — `App.Init()`: delegates to the initial view's `Init()` and, when enabled, arms the app-level auto-refresh ticker (see `auto_refresh.go`).
- **`auto_refresh.go`** — app-level 1s ticker infrastructure remains for the global setting, but `autoRefreshActiveView` returns no command for `/kanban` (or any current root view). Kanban is manual-only: entry, selected-agent change, and explicit Ctrl+R each launch the same asynchronous bounded snapshot. There is no `PropsModel.AutoReloadCmd`, live badge, or one-second filesystem path (`tui/internal/tui/auto_refresh.go:35-40`; `tui/internal/tui/props.go:150-277`).
- **`tui/internal/tui/app.go:341-865`** — `App.Update()`: the central dispatcher. It records full terminal size only for raw `tea.WindowSizeMsg`, derives the child content rectangle from the root `LayoutBudget`, and forwards that rectangle through the shared child resize dispatcher (`tui/internal/tui/app.go:346-358`, `tui/internal/tui/app.go:1654-1697`). Root cross-view routing sends `mailRefreshMsg`, its side-effect-free `mailPersistMsg` continuation, cached `networkActivityMsg`, `homeTelemetryMsg`, and `homeAsyncStatsMsg` follow-ups to the preserved Mail model regardless of whether Projects/Help is active, returning immediately so the active child is neither changed nor double-dispatched (`tui/internal/tui/app.go:398-404`). `ProjectsAgentSelectedMsg` remains root-owned (`tui/internal/tui/app.go:524-528`); root keys, including `ctrl+c`, stay available before child dispatch. Mail `Ctrl+G` and `tea.KeyF2` routing precedes focused-rail key consumption; either key toggles at width 85 or greater when copy mode and Mail-owned overlays are inactive, while every ineligible occurrence is consumed without child dispatch. `toggleAgentRail` releases focused-rail focus on collapse and synchronously forwards the new child rectangle in the same update (`tui/internal/tui/app.go:739-781`, `tui/internal/tui/app.go:1496-1520`).
- **`tui/internal/tui/app.go:809-1168`** — `openSetupCredentials` plus `handlePaletteCommand`: maps slash-command strings to view transitions (`/doctor` → `appViewDoctor`, `/daemons` → `appViewDaemons`, `/notification` → `appViewNotification`, `/knowledge` → `appViewKnowledge` (canonical; hidden `/library` and `/codex` aliases), `/skills` → `appViewLibrary`, etc.) and direct actions (`/suspend`, `/cpr`, `/refresh`, `/clear`, `/molt`, `/btw`, `/goal`, `/export`). It derives one validated agent target from `MailModel.currentDirectTarget()`, falling back to Main, and uses that target for every agent-scoped action and agent-owned view while project/global commands retain their existing root routing. `/login` is a compatibility shortcut into Setup → Credentials; `/setup credentials` jumps there directly while plain `/setup` opens `FirstRunModel` setup mode.
- **`tui/internal/tui/app.go:1506-1600`** — visit context helpers: `enterVisitedAgent` preserves exactly one original context plus the origin view/model when entering from `/projects`, switches `projectDir`/focused agent/human mailbox to the selected running agent's project, opens mail, and sets the target mail title's inline `Esc Esc` hint; `returnFromVisit` restores the original mail model/context with that hint cleared and returns either to the preserved `/projects` model or to mail; `maybeHandleVisitEsc` implements the 600ms double-Esc return window.
- **`tui/internal/tui/app.go:1622-1739`** — `switchToView(viewName string)`: the canonical route-to-view dispatcher used by `ViewChangeMsg` and palette commands returning to a view. Reconstructs models fresh on entry; `setup` routes to `FirstRunModel` setup mode and `login` reconstructs the Setup → Credentials model for the legacy `/login` shortcut. Entering `/projects` passes `ProjectsContext` from root state so the child can mark current/original/visiting rows without owning the transition (`tui/internal/tui/app.go:1719-1720`).
- **`tui/internal/tui/app.go:2060-2138`** — `App.View()`: delegates to the current view's `View()` for child content, horizontally joins the optional Mail rail, then wraps the result with root-owned chrome via `composeWithChrome` BEFORE building `tea.NewView` (alt-screen + mouse mode). The startup banner and non-mail select-mode indicator are root chrome, so they occupy rows the child yielded instead of extending the terminal frame. The visit indication is not root chrome; target Mail renders it inline in its title row. The final Mail frame copies `MailModel.Cursor()`, adds only the resolved `LayoutBudget.RailWidth` and `TopChromeRows`, and publishes that physical cursor on the final `tea.View`; every non-Mail view keeps a nil cursor (`tui/internal/tui/app.go:2129-2136`). Copy/select mode still changes `MouseModeCellMotion` to `MouseModeNone` independently of cursor projection (`tui/internal/tui/app.go:2116-2128`).
- **`tui/internal/tui/app.go:1496-1504`** — `App.sendSize()`: returns a `tea.Cmd` carrying the root budget's child content rectangle in a root-internal `childWindowSizeMsg`, so freshly routed and raw-resized views agree on horizontal and vertical geometry without making the root treat a synthetic child size as a raw terminal resize.
- **`tui/internal/tui/app.go:1807-1916`** — portal launch and browser-open helpers; `SetTUIVersion` lives with doctor version diagnostics (`tui/internal/tui/doctor.go:30-35`).

### Root layout budget (`layout.go`)

- **`tui/internal/tui/layout.go:13-129`** — the root-owned vertical and horizontal layout contract. `LayoutBudget` names full terminal width, child content width, rail width/visibility, minimum chat width, root chrome rows, and child height. `agentRailMinTerminalWidth` owns the 85-column threshold. `App.layoutBudget()` requests the 24-column rail only for Mail at that width or greater while `agentRailState.explicitlyCollapsed` is false, leaving 61 content columns at the threshold; widths through 84 and every non-Mail view remain full-width. `resolveHorizontalLayout` clamps terminal width, hides disallowed or non-fitting rails without consuming columns, and remains the only horizontal subtraction. `LayoutBudget.ChildWindowSize()` is the one content rectangle consumed by raw and root-synthesized resize paths, while rail rendering and mouse X hit-testing read the same budget.

### Screens

- **`tui/internal/tui/firstrun.go:174-5199`** — `FirstRunModel`. Multi-step wizard with constructors for FOUR flows: `NewFirstRunModel` (new project, persist-immediately; `tui/internal/tui/firstrun.go:459`), `NewDraftFirstRunModel` (no-project launcher's Create flow — draft-only, starts at `stepPickPreset` because the launcher's welcome prelude owns language/theme, see below; `tui/internal/tui/firstrun.go:706`), `NewSetupModeModel` (reconfiguring an existing agent), and `NewRehydrateModel` (cloned network). `NewFirstRunModel` and `NewDraftFirstRunModel` share `newFirstRunModelForPurpose(purpose firstRunPurpose, ...)` (`tui/internal/tui/firstrun.go:484`) and pass `purposeNormal`/`purposeDraft` directly, so draft purpose is applied via `withPurpose` BEFORE the config-loader and Claude-auth branches run. `NewSetupModeModel`/`NewRehydrateModel` deliberately preserve historical construction by calling `NewFirstRunModel` first and retagging with `purposeSetup`/`purposeRehydrate` afterward; no setup/rehydrate behavior branches on `purpose` during construction. Its background bootstrap calls `config.EnsureRuntimeQuiet`, so first-run venv creation is followed by the same non-blocking Python `lingtai` upgrade check as returning-user startup — EXCEPT in draftMode, where `Init()` (`tui/internal/tui/firstrun.go:878`) skips bootstrap entirely (zero-write invariant; real bootstrap happens post-commit in `project_create.go`). Steps (`firstRunStep` enum, `tui/internal/tui/firstrun.go:96-112`): Welcome → API Key → Pick Preset → Edit Preset → Preset Key → Capabilities → Agent Presets → Agent Name/Dir → Recipe → Recipe Swap Confirm (mid-life only) → **Review (draftMode only)** → (optional) Rehydrate Propagate → Launching. The draft flow ENTERS at Pick Preset and never visits Welcome/API Key (the launcher prelude collected language/theme; the picker is always reachable regardless of on-disk presets). The Codex credential row behaviour is mode-split: in first-run (non-setupMode) it opens the inline two-method login chooser — browser OAuth/localhost or device code — both routed through `startCodexLogin`; in setupMode (`/setup`) it emits `ViewChangeMsg{View:"login"}` (`tui/internal/tui/firstrun.go:1520`) to hand off to the dedicated Setup → Credentials subpage instead. Pressing Esc while a Codex login is mid-flight or the method chooser is open cancels that login and stays on the picker rather than exiting to home. Codex preset selectability is judged per-preset by `presetCredentialState`. First-run manages the primary (legacy) account; additional accounts are added from Setup → Credentials. **Draft-mode Codex Delete is refused for pre-existing disk auth** (`tui/internal/tui/firstrun.go:1631-1634`): `m.codexAuth.valid` reflects real on-disk `codex-auth.json` regardless of `draftMode` (`refreshCodexAuth` reads it unconditionally at construction), so the two-press Del/logout arm is blocked entirely — with a localized `firstrun.preset_pick.draft_codex_logout_blocked` message, never a false "logged out" state — whenever `draft.DraftCodexTokens` is still empty (i.e. the auth predates this draft session). When a login instead completed DURING this draft session (`CodexOAuthDoneMsg`'s draftMode branch populates `DraftCodexTokens`), Delete remains fully functional (nothing was ever written to disk to begin with). The Claude Code auth row is hidden for now (unsupported); detection (`refreshClaudeCodeAuth` / `claudeCodeAuthConfigured`) still runs and feeds the `claude-code` credential guard for `purposeNormal`/`purposeSetup`/`purposeRehydrate` — `purposeDraft` skips this probe entirely (subprocess exec, unnecessary for a hidden row during a session that may never commit). Emits `FirstRunDoneMsg` when complete.
- **Typed purpose discriminator (`firstRunPurpose`)** — `tui/internal/tui/firstrun.go:402-431` defines `type firstRunPurpose int` (`purposeNormal`/`purposeSetup`/`purposeRehydrate`/`purposeDraft`) and `(m FirstRunModel) withPurpose(p firstRunPurpose) FirstRunModel`, which sets both `m.purpose` and a derived `m.draftMode bool` cache atomically (`tui/internal/tui/firstrun.go:385-394` for the fields). `draftMode` is kept as a genuine field rather than becoming a method specifically so its ~13 existing `if m.draftMode` call sites across this file's credential/persist paths did not need to change shape — `withPurpose` is the single point that can set it, so the two never disagree. `purposeSetup`/`purposeRehydrate` are set (for honesty) but nothing branches on them yet beyond `purposeDraft`'s special-cased reads in `newFirstRunModelForPurpose`; a full replacement of the separate `setupMode`/`rehydrateMode` booleans (~60 call sites) was judged out of scope for a single pass.
- **Draft-purpose routing (`draftMode`/`purposeDraft`)** — disk-mutating calls remain guarded so draft choices stay in `ProjectDraft` until `ProjectDraftConfirmedMsg` reaches `RunProjectCreate`; the draft flow starts at `stepPickPreset`, uses the review step, and emits typed cancel/confirm messages. The wizard no longer renders a persistent draft-status line; zero-write navigation is enforced by guarded mutation paths, then the finalizer builds and validates staging, persists launch dependencies, and publishes with one rename (`tui/internal/tui/firstrun.go:1043-1141`, `tui/internal/tui/firstrun.go:1248-1261`, `tui/internal/tui/firstrun.go:2678-2700`, `tui/internal/tui/project_create.go:326-563`). The recipe picker is gone: the TUI now always commits the `adaptive` recipe (`preset.DefaultRecipe`), and `copyRecipeBundle` (`tui/internal/tui/recipe_save.go`) falls back to the compiled-in bundle via `preset.CopyEmbeddedBundle` when no disk-backed `<globalDir>/recipes` tree exists yet (fresh home before `preset.Bootstrap`); a project that already ships its own `.recipe/` keeps its local bundle instead of being re-staged.
- **`MailModel` / windowed history** (`tui/internal/tui/mail.go:176-411`, `tui/internal/tui/mail.go:909-1168`) — The network home screen owns async session reconstruction, chronological message rendering, compose input, and finite history reveal. Displayed mail rows are projected exactly once from Main MailModel's private `acceptedMailSnapshot` (`tui/internal/tui/mail_snapshot.go:9-23`) in both the default and `ctrl+o` layers; the live `fs.MailCache` remains the sole producer; the deep clone is now prepared inside the detached refresh command itself and published only after the existing generation gate plus the one monotonic refresh request serial/newest-accepted watermark accept its completion (`tui/internal/tui/mail.go:995-1012`). `buildMessages` consumes a detached snapshot copy, so producer-only refresh work and aliases cannot leak into render/history consumers; derived `SessionCache` mail copies are skipped while non-mail event replay remains unchanged. There is no `ProjectMailStore`, second scanner, second freshness coordinate, or Agent view in this seam; the one refresh request serial issued on the Update loop is the only refresh-ordering state. That lane is single-flight: timer/manual requests collapse into one pending demand while one prepared refresh runs, only the owning serial releases it, and that completion immediately launches the one follow-up. Project network activity is no longer built inside `refreshMail`; a separate generation-gated in-flight/one-second-TTL command owns the cached badge snapshot. Home async counts/tokens/models likewise consume one bounded dispatch-ledger snapshot with no lifetime daemon-directory listing. A separate monotonic Mail poll epoch identifies the one current refresh-tick/pulse chain inside an activation: every Mail loop start advances it, and stale same-generation timer messages are rejected before refresh, animation, telemetry, or rearm (`tui/internal/tui/mail.go`, `tui/internal/tui/home_async_stats.go`, `tui/internal/tui/app.go`). ## Notes

- **~19k LOC in one package is deliberate, not a refactor debt.** Bubble Tea's `tea.Model` interface requires every model to be the same Go interface type. Splitting screens into sub-packages would either (a) require import cycles (the root model dispatches to sub-package models, but sub-package models emit cross-view messages consumed by the root) or (b) require an interface-indirection layer that fights Bubble Tea's convention. The lint is correct here: this is the grain that fits the framework.
- **Screen-per-file is the convention, not a strict rule.** `firstrun.go` (4477 lines) combines the wizard with embedded sub-models (preset editor, skill files browser). `firstrun.go` is the largest single file because the wizard is a modal flow where steps share internal state (selected preset, agent name, recipe) that's harder to split cleanly.
- **All screens are eagerly constructed in `App` as zero-value fields** — only the active view gets a `New*Model()` call. When switching views, `switchToView` reconstructs the model fresh.
- **Paste delivery requires forwarding `tea.PasteMsg`** alongside `tea.KeyPressMsg`. The `InputModel` handles this; any text widget embedded in another model must forward paste messages in its host's `Update()`.
- **`textarea` over `textinput`** for paste-friendly fields (API keys, base URLs). Apply `themedTextareaStyles()` from `styles.go` — bare `textarea.New()` renders a dark cursor that clashes with the warm theme.
- **Mail-view chat replay: verbosity gate + render switch.** `MailModel.verbose` (`tui/internal/tui/mail.go:82-88`) is a 3-state enum (`verboseOff` → `verboseThinking` → `verboseExtended`) cycled by `ctrl+o`, but only two verbose layers exist beyond normal mail. Two coupled switches gate every rendered event: `shouldShow` (`tui/internal/tui/mail.go:471-502`) decides which `SessionEntry` types are visible at the current level, and `renderMessages` (`tui/internal/tui/mail.go:942-1246`) maps each `ChatMessage.Type` to a styled block. `verboseThinking` shows text/inner-state/kernel diagnostics — `thinking`, `diary`, `text_input`, `text_output`, `soul_flow`, `notification`, `aed` — plus compact progress markers: `tool_call` uses the first rendered line capped after the first 400 runes, while `tool_result` uses the first rendered line. `verboseExtended` shows full `tool_call` and `tool_result` bodies (still subject to render-time truncation). Verbose LLM-round-trip entries inherit the current `api_call_id` and are visually separated when that id changes (`apiCallGroupSeparatorBefore` in `toolcall_display.go`), so separate API responses do not run together in ctrl+o while mixed entries from the same API call stay grouped. Tool entries get a faint local `15:04` timestamp (`formatToolTimestamp`); `tool_call` uses `compactToolCallSummary` at level 1, `tool_result` uses `firstRenderedLine` at level 1, and both use `truncateToolBody` at level 2 (all in `toolcall_display.go`). Legacy tool entries without grouping metadata keep the old `tool_result`→`tool_call` fallback (`toolGroupSeparatorBefore`). `fs/session.go` carries full tool args/results into the mail replay; its `appendToolResultMetaBlocks` detects whether a tool_result carries any of the `_meta` envelope blocks (`_tool`, `_runtime.state`, `_runtime.guidance`, `notifications`, `_notification_guidance`) and, rather than expanding that noise inline, emits a single localized hint line (`i18n.T("mail.meta_hidden_hint")`) pointing the user at `/notification`, where the full canonical `_meta.*` envelope is paged on demand (see `notification.go`). The raw metadata stays in the underlying event and is stripped from the `result:` body by `displayToolResultValue`, so nothing is lost — only hidden. Render-time truncation is still applied by `MailModel.verbose` and `MailModel.toolCallTruncate`. **Per-round token usage footer:** `fs/session.go`'s `parseEventMap` lifts the four scalar token fields (`input_tokens`, `output_tokens`, `cached_tokens`, `estimated`) off each `llm_response` event into `SessionEntry.TokenUsage` (`fs.TokenUsage`) — never the hidden `_meta` envelope. The `llm_response` carrier sits at the *top* of its `api_call_id` group in stream order, so `renderMessages` defers a single faint footer line (`formatTokenUsageFooter`, `tui/internal/tui/token_usage_footer.go:30`) to the *bottom* of the group via a `pendingUsage`/`flushTokenFooter` accumulator: `tokens: input … · cache miss … · output … · cache rate …` (localized `mail.token_usage_footer`, counts humanized by `humanizeTokenCount`, miss/rate reuse `cacheMiss`/`formatCacheRate` from `props.go`), plus an optional trailing `· API: x.x s` segment (localized `mail.token_usage_footer_api`, seconds via `formatApiCallSeconds`) fed by `TokenUsage.ApiDurationMs` — the kernel-measured `provider_wait_ms` provider round-trip lifted off the same `llm_response` event; events predating that kernel telemetry carry 0 and keep the unchanged four-segment footer. `shouldShow` lets an `llm_response` through only when it carries `TokenUsage` and `verbose >= verboseThinking`; it never renders as a raw `[llm_response]` block. Soul flow and notification share the green palette (`ColorAccent` bold header, `ColorAgent` italic body indented 4) — they're agent-side reflections. AED uses the orange `ColorTool` palette to mark kernel distress (LLM empty-response retries, recovery timeouts) so it stands out from normal inner state. **A-priori summary (`summary=true`, kernel PR #586):** when an agent runs `bash`/`read`/`grep` with `summary=true`, the kernel preserves the RAW result in the `tool_result` event (so the raw stdout still renders unchanged) and replaces the *model-visible* payload with a generated summary artifact (`lingtai_apriori_tool_result_summary`). `fs/session.go` surfaces that artifact two ways: it promotes the kernel's `apriori_summary_generated`/`apriori_summary_cap_refused`/`apriori_summary_failed`/`apriori_summary_empty`/`apriori_summary_no_summarizer` lifecycle events into a first-class `apriori_summary` `SessionEntry` (carrying `SessionEntry.Summary` = `fs.AprioriSummary` with kind/tool_call_id/char-counts, and — as of kernel #3833 — the generated summary text on the success path via `generated_summary`; pre-#3833 logs lack it and `Text` stays empty), and — defensively — detects the same artifact when it appears as a `tool_result` event's `result` map (`aprioriSummaryFromArtifact`), attaching it to that `tool_result` entry. `renderMessages` renders the model-visible summary as a distinct labelled block (`renderAprioriSummaryBlock` in `toolcall_display.go`) right after the corresponding raw `tool_result`: `ColorAccent` bold label (`mail.apriori_summary_label`), italic `ColorAgent` summary text, and a faint compression footer (`tool · orig → summary chars · raw preserved`). Cap-refusal / fail-closed variants (`Unavailable`) switch to the `ColorTool` palette and the `mail.apriori_summary_unavailable_label`. The generated summary text itself follows the two-layer ctrl+o convention via `renderAprioriSummaryBlock`'s `preview` arg (passed `m.verbose != verboseExtended`): the FIRST layer (`verboseThinking`) shows only a 200-rune preview of the summary text (`previewSummaryText`, `aprioriSummaryPreviewLimit`, trailing `…` only when longer), and the DEEPER layer (`verboseExtended`) shows the full summary. Only the generated text is previewed — the label, footer, fallback no-text note, and cap/error messages always render whole. The summary shares its raw result's `api_call_id` (`apriori_summary` is in `isApiGroupedVerboseMessageType`), so it stays grouped directly under the raw block with no separator; `shouldShow` gates it at `verboseThinking` like the tool entries it accompanies. To add a new event type to the chat replay, extend `fs/session.go`'s `parseEvent` (allow-list + body extractor), then both `shouldShow` and `renderMessages` here.

- **Home telemetry row (additive, current-session scope).** `MailModel.View()` (`tui/internal/tui/mail.go:2244`) appends one muted, high-density line BELOW the input box and ABOVE the path/shortcut status bar — additive, never replacing the pre-existing footer/status content. It shows the CURRENT SESSION's token economy plus live context pressure, led by a localized scope label and closed by a right-aligned `/kanban for details` affordance: `Session:  llm zhipu/glm-5.2  api 42  tok 181.6k (miss 1.4k)  cache 88%  ctx 186.5k/250.0k ▓▓▓░░ 75%          /kanban for details`. The row is built in `home_telemetry.go` — `MailModel.gatherHomeTelemetry` (`tui/internal/tui/home_telemetry.go:241`) resolves the scalars from ONE `fs.ReadAgentRecord(orchestrator)` read (`tui/internal/fs/agent_record.go:65`), the kernel-published, versioned `system/agent_record.json` (schema `lingtai.agent_record/v1`, kernel #1423, `lingtai-kernel src/lingtai/kernel/session_stats`) — direct migration from the former `.status.json` + `init.json`/`manifest.resolved.json` pair, and this record is the kernel's sole source for normal live status. All numbers are scoped to the **current molt session** (not the whole-ledger lifetime total, not a single round): API calls / session tokens / cached / input come from `record.Usage` (`api_calls`, `input_tokens`, `output_tokens`, `thinking_tokens`, `cached_tokens`); the active configured provider/model pair comes from `record.Model` (`provider`, `model`). Context usage/used/window come from that SAME record's `Usage` block (`context_used_tokens`, `context_limit_tokens`, `context_usage_pct`), gated on `ContextLimitTokens > 0` exactly mirroring the former `.status.json` `WindowSize > 0` gate — a context window the kernel has not resolved yet (e.g. `agent._chat` not initialized) publishes `null`/`0` rather than a fabricated pair. **There is no fallback of any kind**: a missing `system/agent_record.json`, a JSON syntax error, a field-type mismatch, or an unrecognized `schema` value all make `fs.ReadAgentRecord` return `ok=false`, and `gatherHomeTelemetry` returns the all-zero/-1 sentinel telemetry (the row hides) — never a reconstruction from `.status.json`, heartbeat files, the manifest, or raw `logs/events.jsonl` notifications (the pre-migration Ctrl+O/PR #443 notification fallback was removed with this migration, since it duplicated the record's own live context truth from a second, unversioned source). `formatHomeTelemetry` (`tui/internal/tui/home_telemetry.go:321`) leads the row with a localized scope label (`i18n.T("mail.telemetry_session")` — Jason's final follow-up trimmed the verbose "Current Session" to the compact `Session:` (en/wen) / `当前` (zh), never hard-coded; Jason msg 3217, zh wording follow-up). The trailing colon now carries the set-off the `·` middle-dot used to, so the bullet is dropped and the label reads `Session:  api 42 …`. Then it renders the economy fragments (each dropped when its source is zero, so a missing piece never shows a `0`) — the `tok` total carries a `(miss …)` suffix glued directly after it (Jason's explicit placement: right after `tok …`, NOT after the cache percentage), the cache-miss token count = `input − cached` via `cacheMiss` (`props.go`, clamped ≥0 so `cached > input` never prints negative) humanized by `humanizeTokenCount`, gated on `inputTokens > 0` so a session with no recorded input never shows a bare `(miss 0)` (i18n key `mail.telemetry_miss`: `miss` en / `未命中` zh / `漏` wen) — cache rate via `formatCacheRate` (`props.go`) — then the context segment `i18n.T("mail.telemetry_context")` (the technical abbreviation `ctx` in en/wen, `上下文` in zh — Jason's final follow-up trimming the verbose "Current Context") + `used/limit` + gauge + `N%` on the right of the bar (Jason's layout follow-up msg 3251: explicit scope label, then used/limit, then bar, then percentage — never the confusing percentage-first `N% / limit`), then `appendKanbanHint` (`tui/internal/tui/home_telemetry.go:465`) right-aligns the localized `i18n.T("mail.telemetry_kanban_hint")` affordance against the terminal width (status-bar pad style; dropped when there's <2 cols of gap so the metrics never clip), or returns "" when no data is available (graceful hide). `renderContextBar` (`tui/internal/tui/home_telemetry.go:507`) draws a `▓`/`░` gauge colored by pressure (`ColorActive` <70% → `ColorAccent` 70–89% → `ColorSuspended` ≥90%); the bar adapts to terminal width and is dropped below width 40. Scalar-only — never the hidden `_meta` envelope. **Display expression (default + replaceable):** the row is assembled from a single named default expression, `defaultHomeTelemetryDisplay` (`tui/internal/tui/home_telemetry.go:114`) — the six slots in their default visual order, `session` (the localized `Session:` scope label) · `llm` (the configured provider/model pair) · `api` (API calls) · `tokens` (the `tok` total with its glued `(miss …)` suffix) · `cache` (cache rate) · `context` (the `ctx` used/limit + gauge + percentage segment). There is no `tok/api` slot. The expression is walked by `homeTelemetrySegments` (`tui/internal/tui/home_telemetry.go:352`) over `homeTelemetryFragment` (`tui/internal/tui/home_telemetry.go:376`), the ONE place each fragment's text is built; a slot whose source is unknown is dropped, exactly as before. That default is the persistent behavior: with no preference set the row renders byte-for-byte what it always has. A user may replace it with an ordered selection of the SAME fragments through the optional `home_telemetry_display` key in TUI-owned `~/.lingtai-tui/tui_config.json` (`config.TUIConfig.HomeTelemetryDisplay`, `tui/internal/config/ANATOMY.md`), applied to `MailModel.homeTelemetryDisplay` at `App.installMailModel` (`tui/internal/tui/app.go:128`) — the one app-owned boundary every real construction and restore path goes through, so `NewMailModel`'s signature stays free of it — and re-applied on the settings-return path (`tui/internal/tui/app.go`) exactly like `toolCallTruncate`, which additionally recomputes `syncViewportHeight` when the new expression flips the row's visibility. The expression is **selection and order only** — it is not a template, format string, metric, color, or width, it adds no settings UI, no watcher, and no new i18n string, and it cannot reach past the one Agent Record read above. Validation is **fail-closed wholesale** and lives one layer down, in `config.NormalizeHomeTelemetryDisplay` (`tui/internal/config/global.go:177`): absent, empty, over-long, repeated, or unknown-name yields `nil` and the default expression renders, because a partially honored expression would silently drop the fragment the user misspelled. `LoadTUIConfig` and `SaveTUIConfig` both apply it, exactly like `NormalizeMailPageSize`, so an invalid expression is **discarded at load and omitted at save** — changing an unrelated preference in `/settings` can never re-write a typo as durable config — while the other preferences in the file survive untouched. `homeTelemetryDisplayFromConfig` (`tui/internal/tui/home_telemetry.go:126`) is the renderer's single entry point (called at install / settings return, never per frame) and only maps the accepted names onto fragments. The vocabulary and the default order are ONE declaration, `config.AllowedHomeTelemetryDisplay` (`tui/internal/config/global.go:162`), from which `defaultHomeTelemetryDisplay` is derived, so what the row renders and what the file accepts cannot drift. The right-aligned `/kanban` affordance and the width-dependent context-bar layout stay renderer/layout behavior below the expression — no expression can move, repeat, or remove them. When a valid expression selects only fragments this snapshot has nothing for, the row hides **and no footer line is reserved for it**: `hasHomeTelemetry` and `formatHomeTelemetry` both ask `homeTelemetrySegments`, so the height budget and the render are one decision — no blank reserved row, no clipped status bar. `/kanban` remains a separate consumer, but it now uses a bounded manual snapshot and performs no render-time or whole-ledger read. **Height accounting:** because the row is additive, `mailFooterHeight` (`tui/internal/tui/home_telemetry.go:307`) is the single source of truth for footer rows (`sep + palette + input + optional telemetry + border + status`), and `syncViewportHeight` (`tui/internal/tui/mail.go:403`) reserves the telemetry line via `hasHomeTelemetry` (`tui/internal/tui/home_telemetry.go:297`) — the single no-I/O visibility predicate, which reads the cached snapshot AND the selected expression, and is the same predicate used by `View`, by `applyHomeTelemetry`'s visibility-change check, and on the settings-return path — and re-syncs when its visibility flips (`lastTelemetryRows`). Without this reservation the frame renders one line too tall and the bottom status bar (the `ctrl+o to expand` hint) is clipped off-screen (the #441 regression). **Status-bar hint copy:** the home/mail footer's right-aligned shortcut hint reads `ctrl+o to expand, / for commands` in the English UI (`hints.verbose`/`hints.verbose_on` + localized `hints.sep` + `hints.commands`, rendered in `mail.go` ~`1436-1451`); zh/wen keep the bullet separator and their own wording. These three i18n keys are home-footer-exclusive, so the copy is safe to change without touching other screens — the visible prompt no longer says `soul` (Jason msg #3254 follow-up to PR #445, which had cleaned only `ctrl+e editor`).
